# CRM运营平台 - 应用清单与部署配置

## 1. 产品层级说明

### 1.1 层级定义

```
平台 (Platform)
  └── 应用 (Application)
      └── 功能 (Feature)
          └── 操作 (Operation)
```

**当前平台：** CRM运营平台（CRM Operation Platform）

### 1.2 架构原则

**一个应用 = 一个微服务 + 一个数据库 + 一个微前端**

```
┌─────────────────────────────────────┐
│         Application (应用)           │
├─────────────────────────────────────┤
│ ┌─────────────────────────────────┐ │
│ │     Micro Frontend (微前端)      │ │
│ └─────────────────────────────────┘ │
│                 ↓                    │
│ ┌─────────────────────────────────┐ │
│ │     Microservice (微服务)        │ │
│ └─────────────────────────────────┘ │
│                 ↓                    │
│ ┌─────────────────────────────────┐ │
│ │      Database (数据库)           │ │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

## 3. 服务发现策略

> **重要提示**：本平台使用 **Spring Boot 3.2.x + Spring Cloud 2023.0.x**，配置方式与旧版本有所不同：
> - ✅ **不再需要** `bootstrap.yml` 文件
> - ✅ **统一使用** `application.yml` 进行配置
> - ✅ **必须使用** `spring.config.import` 从 Nacos 导入配置
> - ❌ 禁止使用 `bootstrap.yml`，如有需要请联系架构组

### 3.1 推荐方案：Nacos统一服务发现

**核心思想：** 无论K8S还是本地部署，统一使用Nacos进行服务注册与发现。

#### 优势
1. **环境一致性**：开发、测试、生产环境使用相同的服务发现机制
2. **配置统一**：统一的配置中心，配置热更新
3. **灵活性**：支持多数据中心、灰度发布等高级特性
4. **可观测性**：Nacos控制台可视化管理所有应用
5. **Spring Cloud生态**：与Spring Cloud无缝集成

#### 架构图

```
┌─────────────────────────────────────────────────────────────┐
│                    Client / API Gateway                     │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    Spring Cloud Gateway                     │
│              (从Nacos获取服务列表进行路由)                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
                     ┌──────────────┐
                     │    Nacos     │
                     │ 注册中心/配置  │
                     └──────────────┘
                            ↑
        ┌───────────────────┼───────────────────┐
        │                   │                   │
    ┌───────┐          ┌───────┐          ┌───────┐
    │Service│          │Service│          │Service│
    │   A   │          │   B   │          │   C   │
    └───────┘          └───────┘          └───────┘
```

## 4. 应用间调用配置

### 4.1 Spring Boot配置（application.yml）

> **注意**：Spring Boot 3.x 不再需要 `bootstrap.yml`，统一使用 `application.yml` + `spring.config.import` 从 Nacos 导入配置。

**以租户应用为例：**

```yaml
spring:
  application:
    name: crm-operation-tenant  # 服务名
  # Spring Boot 3.x 使用 spring.config.import 导入Nacos配置
  config:
    import:
      - optional:nacos:${spring.application.name}.yaml?group=TENANT_GROUP
      - optional:nacos:common-database.yaml?group=COMMON_GROUP
      - optional:nacos:common-redis.yaml?group=COMMON_GROUP
      - optional:nacos:common-logging.yaml?group=COMMON_GROUP
  cloud:
    nacos:
      # Nacos服务器地址
      server-addr: ${NACOS_SERVER_ADDR:localhost:8848}
      # 服务发现配置
      discovery:
        namespace: ${NACOS_NAMESPACE:operation-dev}
        group: TENANT_GROUP
        # K8S环境下使用IP注册
        ip: ${POD_IP:}
        # 注册端口
        port: ${SERVER_PORT:18102}
      # 配置中心
      config:
        namespace: ${NACOS_NAMESPACE:operation-dev}
        file-extension: yaml

server:
  port: ${SERVER_PORT:18102}

# 开启Nacos服务发现
feign:
  client:
    config:
      default:
        connectTimeout: 5000
        readTimeout: 10000
```

#### Nacos端口配置说明

**Nacos 2.x 端口体系：**

| 端口 | 用途 | 说明 |
|------|------|------|
| 8848 | HTTP API | Web控制台、REST接口、Python脚本调用 |
| 9848 | 客户端gRPC | Spring应用连接（= 8848 + 1000） |
| 9849 | 服务端gRPC | Nacos集群间通信（= 8848 + 1001） |

**本地开发环境（docker-compose）：**

```yaml
# docker-compose.yml
services:
  nacos:
    ports:
      - "31848:8848"   # HTTP API（控制台、REST接口）
      - "31850:9848"   # 客户端gRPC（Spring应用连接）
      - "31851:9849"   # 服务端gRPC（集群间通信）
```

**⚠️ gRPC端口偏移量问题：**

当Nacos HTTP端口**不是8848**时（如映射到31848），Spring应用需要**显式设置gRPC端口偏移量**，否则会连接失败。

**解决方案：在应用启动类添加静态初始化块**

```java
@SpringBootApplication
public class SystemApplication {
    
    // 设置Nacos客户端gRPC端口偏移量
    // 31848 + 2 = 31850（对应docker-compose中的9848映射）
    static {
        System.setProperty("nacos.server.grpc.port.offset", "2");
    }
    
    public static void main(String[] args) {
        SpringApplication.run(SystemApplication.class, args);
    }
}
```

**计算公式：**
- 客户端gRPC端口 = HTTP端口 + 1000 = 31848 + 1000 = 32848（容器内）
- 映射到宿主机 = 31850
- 偏移量 = 31850 - 31848 = 2

**生产环境（K8S）：**

生产环境Nacos使用标准端口8848，无需设置偏移量。可以通过**环境变量或配置文件**动态控制：

```java
static {
    // 仅本地开发环境设置
    if ("dev".equals(System.getProperty("spring.profiles.active"))) {
        System.setProperty("nacos.server.grpc.port.offset", "2");
    }
}
```

#### spring.config.import 详解

**基本语法：**
```yaml
spring:
  config:
    import: optional:nacos:{dataId}.yaml?group={group}
```

**参数说明：**
- `optional:` - 表示即使 Nacos 配置不存在也不会启动失败（推荐使用）
- `nacos:` - 指定从 Nacos 导入配置
- `{dataId}` - 配置文件的 Data ID
- `?group={group}` - 指定配置所在的 Group（必须）

**完整配置示例（各应用通用模板）：**

```yaml
spring:
  application:
    name: crm-operation-{app}  # {app} 替换为具体应用名
  config:
    import:
      # 应用特定配置（需指定对应的 Group）
      - optional:nacos:${spring.application.name}.yaml?group={APP}_GROUP
      # 公共配置（从 COMMON_GROUP 导入）
      - optional:nacos:common-database.yaml?group=COMMON_GROUP
      - optional:nacos:common-redis.yaml?group=COMMON_GROUP
      - optional:nacos:common-logging.yaml?group=COMMON_GROUP
      # 可选：RabbitMQ配置（如需要）
      # - optional:nacos:common-rabbitmq.yaml?group=COMMON_GROUP
```

#### 配置优先级

配置的加载优先级（从高到低）：
1. 命令行参数
2. `application-{profile}.yml`（本地文件）
3. `application.yml`（本地文件）
4. Nacos 配置中心 - 应用特定配置（如 `crm-operation-tenant.yaml`）
5. Nacos 配置中心 - 公共配置（如 `common-database.yaml`）

**说明：**
- 后导入的配置会覆盖先导入的配置
- 应用特定配置会覆盖公共配置
- 本地配置会覆盖 Nacos 配置

#### 配置管理最佳实践

**1. 配置分离原则**
- ✅ 本地 `application.yml` 只保留启动必需配置（应用名、Nacos地址、端口）
- ✅ 业务配置、数据库配置全部放在 Nacos 配置中心
- ✅ 敏感信息（密码、密钥）使用环境变量注入，不直接写入配置

**2. 公共配置复用**
- ✅ 多个应用共用的配置（数据库连接池、Redis配置等）放入 `COMMON_GROUP`
- ✅ 应用特定配置放入各自的 Group
- ✅ 避免配置重复，提高维护效率

**3. 按应用分组的优势**
- ✅ **权限隔离**：可为不同 Group 设置不同的访问权限，增强安全性
- ✅ **清晰直观**：配置组织与应用架构完全对应，易于理解和维护
- ✅ **独立管理**：每个应用的配置独立，互不干扰
- ✅ **团队协作**：不同团队可以独立维护各自应用的配置

**4. 配置变更流程**
1. 在 Nacos 控制台修改对应的配置文件
2. 配置自动推送到订阅该配置的应用
3. 应用监听配置变更，动态刷新（使用 `@RefreshScope` 注解）
4. 无需重启应用即可生效（支持热更新的配置项）

**5. 环境隔离**
- 开发环境：`operation-dev`
- 测试环境：`operation-test`
- UAT环境：`operation-uat`
- 生产环境：`operation-prod`

### 5.2 动态路由（从Nacos配置中心读取）

```java
@Component
public class DynamicRouteService implements ApplicationEventPublisherAware {
    
    @Autowired
    private RouteDefinitionWriter routeDefinitionWriter;
    
    private ApplicationEventPublisher publisher;
    
    /**
     * 从Nacos配置中心加载路由配置
     */
    @NacosConfigListener(dataId = "gateway-routes", groupId = "DEFAULT_GROUP")
    public void onRouteConfigChange(String routes) {
        // 解析并更新路由
        List<RouteDefinition> routeDefinitions = parseRoutes(routes);
        routeDefinitions.forEach(this::updateRoute);
    }
    
    private void updateRoute(RouteDefinition definition) {
        try {
            routeDefinitionWriter.save(Mono.just(definition)).subscribe();
            publisher.publishEvent(new RefreshRoutesEvent(this));
        } catch (Exception e) {
            log.error("更新路由失败", e);
        }
    }
}
```

## 7. 方案对比

### 7.1 方案一：Nacos服务发现（推荐）

| 优点 | 缺点 |
|------|------|
| ✅ 环境一致，开发、测试、生产统一 | ❌ 需要部署Nacos集群 |
| ✅ 配置中心功能，统一配置管理 | ❌ 多一个组件依赖 |
| ✅ 服务治理功能丰富（灰度、流量控制） | |
| ✅ Spring Cloud生态完美集成 | |
| ✅ 可视化管理控制台 | |

### 7.2 方案二：K8S Service + Nacos混合

在K8S中使用Service进行服务发现，本地使用Nacos。

| 优点 | 缺点 |
|------|------|
| ✅ 利用K8S原生能力 | ❌ 开发和生产环境不一致 |
| ✅ 减少外部依赖 | ❌ 需要维护两套配置 |
| | ❌ 无法使用Nacos高级特性 |
| | ❌ 配置管理困难 |

### 7.3 推荐理由

**统一使用Nacos的原因：**

1. **一致性**：开发环境和生产环境使用相同的服务发现机制，减少环境差异导致的问题
2. **Spring Cloud生态**：与Spring Cloud Gateway、Feign、LoadBalancer等完美集成
3. **配置管理**：除了服务发现，还提供配置中心功能，实现配置的统一管理和动态更新
4. **服务治理**：支持灰度发布、流量控制、服务降级等高级特性
5. **可观测性**：提供Web控制台，实时查看应用状态、配置信息

### 8.1 应用命名规范

```
格式：crm-operation-{module}
示例：
- crm-operation-gateway (网关)
- crm-operation-tenant (租户管理应用)
- crm-operation-application (应用管理应用)
```

### 8.2 端口分配规范

```
18100-18199: 应用微服务端口
18100: Gateway
18101-18110: 核心业务应用
18111-18120: 基础服务应用
18121-18130: 扩展应用
```

### 8.3 Nacos命名空间规划

**规范：** 平台名称 + 环境

```
operation-dev:  运营平台开发环境
operation-test: 运营平台测试环境
operation-uat:  运营平台UAT环境
operation-prod: 运营平台生产环境
```

**说明：**
- Namespace ID 和 Namespace 名称保持一致（如 `operation-dev`）
- 便于在Nacos控制台快速识别平台和环境
- 支持未来扩展其他平台（如 `sales-dev`、`service-dev` 等）

### 8.4 Nacos分组规划

**规范：** 按应用分组，每个应用使用独立的 Group

```
GATEWAY_GROUP:          网关应用
SYSTEM_GROUP:           系统管理应用
TENANT_GROUP:           租户管理应用
APPLICATION_GROUP:      应用管理应用
ROLE_TEMPLATE_GROUP:    角色权限模板应用
INFRASTRUCTURE_GROUP:   基础设施应用
WORKFLOW_GROUP:         工作流引擎应用
COMMON_GROUP:           公共配置
```

**命名规则：**
- 应用Group：`{APP}_GROUP`（如 `TENANT_GROUP`）
- 公共配置：`COMMON_GROUP`
- 全部使用大写字母和下划线

**分组与应用映射：**

## 11. 故障排查

### 11.1 应用无法注册到Nacos

**问题排查：**
1. 检查Nacos地址配置是否正确
2. 确认网络连通性（ping/telnet）
3. 查看应用日志中的Nacos相关错误
4. 检查Nacos命名空间和分组配置

**解决方案：**
```bash
# 测试Nacos连通性
curl http://nacos-server:8848/nacos/v1/ns/operator/servers

# 查看应用日志
kubectl logs -f pod-name -n crm-operation
```

### 11.2 应用间调用失败

**问题排查：**
1. 确认目标应用已注册到Nacos
2. 检查Feign/RestTemplate配置
3. 确认微服务名称是否正确
4. 查看负载均衡日志

**解决方案：**
```java
// 添加Feign日志
@Configuration
public class FeignConfig {
    @Bean
    Logger.Level feignLoggerLevel() {
        return Logger.Level.FULL;
    }
}
```
